# privacy-gate v6 设计：把门禁从插件下沉到传输层

> 状态：**待评审的提案**（尚未实现任何代码）
> 目标版本：v6.0.0
> 前置阅读：[DECISIONS.md](../DECISIONS.md) 的 D1（砍掉宏大设计）、D4（门禁框架化）、
> D9（插件格式的真实教训）、D11（引擎失败连锁锁死）、D13（修失败点 ≠ 修失败语义）

---

## 0. 一句话

v5.1 把强制层放在 opencode 的插件 hook 上。v6 把它放到**本地 OpenAI 兼容网关**里——
LLM API 请求的必经之路上。

结果是："哪些数据能出内网"不再依赖任何 Agent 框架的配合，opencode 从"基座"降级为
"适配器之一"。

## 1. 为什么要换：先看清 v5.1 强制层的真实性质

先说清楚耦合面到底有多大（逐文件核对）：

| 层 | 文件 | 可移植性 |
|---|---|---|
| 规则引擎 + 多轮继承 + 决策日志 | `tools/rules_engine.py`（229 行，纯 stdlib） | ✅ 可移植 |
| 纠正回流 | `tools/correct.py`（117 行） | ✅ 可移植 |
| 规则库 / 回归用例 | `keywords/*.json` | ✅ 可移植 |
| 体检 | `check.py`（6 项检查） | ⚠️ 大部分可移植，含 opencode 配置检查 |
| **强制层** | `.opencode/plugins/privacy-gate.js`（277 行） | ❌ opencode 专属 |
| **执行层** | `prompts/worker.md`、`cloud.md`、`opencode.jsonc.example` | ❌ opencode 专属 |

约 500 行核心已经干净，耦合面集中在 **1 个插件 + 2 个 prompt + 1 个配置模板**。

而这个强制层有三个性质，每一个都已经让我们付过代价：

1. **依赖 hook 存在且语义不变**——D9 的 `.ts`/`.js`（桌面端 Node sidecar 加载失败）、
   D11 的 durable event schema（新增 part 缺 id 就保存失败）
2. **依赖 hook 可靠**——`permission.ask` 历史上有 bug 和回归记录，只能作增强层，不能当唯一防线
3. **每换一个基座就要重写一遍**——换成 Claude Code、Cline、DSH，这段 277 行的债要再欠一次

所以本设计**不把门禁搬到"另一个框架"**——那只是把债换个债主。而是搬到**框架之下的公共层**：
LLM API 调用本身。

## 2. 目标架构：三层

```
┌─────────────────────────────────────────────────────────┐
│ 执行层（可替换）：任何 Agent                             │
│   opencode │ Claude Code │ Cline │ Cursor │ 裸脚本       │
└────────────────────────┬────────────────────────────────┘
                         │  OpenAI 兼容请求（base_url 指过来）
                         ▼
┌─────────────────────────────────────────────────────────┐
│ 强制层（新）：本地网关  127.0.0.1:8787                   │
│   分级 → 策略裁决 → 重路由 / 工具剥夺 / 拒绝             │
│   —— 在必经路径上，不需要任何一方配合                    │
└────────────────────────┬────────────────────────────────┘
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
        云端上游               本地上游（Ollama）
      （只接 none）        （medium / high 唯一去处）

┌─────────────────────────────────────────────────────────┐
│ 策略层（你的）：core                                    │
│   引擎 + 词表/规则 + 会话继承 + 决策日志 + 纠正回流      │
│   —— 机制是我们的，边界是你的                            │
└─────────────────────────────────────────────────────────┘
```

## 3. 网关请求管线

### 3.1 会话键推导（唯一有真实设计难度的地方）

OpenAI API **没有会话概念**，而 D6 的多轮隐私继承是按会话建模的。优先级：

1. `x-session-id` 请求头（显式指定，最强）
2. body 的 `user` 字段（OpenAI 标准字段，多数客户端会带）
3. body 的 `metadata.session_id`
4. `sha1(首条 system 消息前 512 字符 + 客户端指纹)`——稳定，但会把不同会话混在一起
5. 兜底 `"default"`

**关键取舍（反直觉但正确）：兜底必须是 `"default"`，而不是"每个请求开一个新会话"。**

- 新会话 = `none` = 解锁远程访问 → **这是最危险的失败方向**
- `default` 共享继承状态 → 宁可过度继承（fail-closed），不可漏继承

代价：单机单用户无感；多个用户共用一个网关实例时会互相污染。
**缓解**：多用户部署必须配 `x-session-id`；网关检测到"最近 N 个请求都没带会话标识"时打警告。

### 3.2 分类对象：只看最后一条 `user` 消息

**不是全部历史。** 理由：历史会累积旧的敏感词，导致会话被永久锁死——一个 high 词进了历史，
后面每一轮都变 high，用户没有任何办法解锁，只能重开会话。

例外：
- 最后一条是 `role: tool`（工具返回）→ 不重新分类，沿用会话级别
- 最后一条是 `role: assistant` → 同上

### 3.3 执行策略

| policy | `none` | `medium` / `high` | 适用 |
|---|---|---|---|
| `reroute`（**默认**） | 转发云端上游 | 转发本地上游 + 改写 `model` | 想要"无感但有效" |
| `block` | 转发云端上游 | 403 + OpenAI 格式错误体 | 合规场景，要留痕 |
| `annotate` | 转发 | 注入标注后原样转发 | 只想观测（兼容 v5.1 行为） |

`reroute` 时改写：`model` → 配置的本地模型名；上游 base_url → 本地上游；其余 body 原样保留。

**为什么默认 `reroute` 而不是 `block`**：`block` 太粗暴，用户会直接把它关掉；
`annotate` 太弱，模型可以无视。`reroute` 是"无声但有效"。
它的代价见 §7 第 2 条——这是个真实的取舍，不是免费的。

### 3.4 远程工具剥夺（核心机制）

`level != none` 时，从请求体 `tools[]` 里**剔除**匹配 `remote_tool_patterns` 的工具：

```json
"remote_tool_patterns": ["*web*", "*fetch*", "*browse*", "*search*", "*crawl*", "*http*"]
```

剔除之后，模型**没有能力**调用远程工具——而不是"被要求不要调用"。
这条路不依赖任何框架 hook，对所有客户端一视同仁。

**诚实的边界**（这些必须写进 README）：
- 按**工具名**匹配 → 命名习惯不同就会漏，使用者需按自己的工具集调模式
- agent 可以用 `bash` 调 `curl` 绕过 → 网关在 LLM API 路径上，管不住任意进程出网（§7 第 1 条）
- 剔除工具后模型可能改用其他可用工具，行为不保证可预测

### 3.5 流式

SSE 原样透传，边读边写，**不缓冲**——本地模型首 token 延迟敏感，缓冲会毁掉体验。

### 3.6 fail-closed 的方向性（v6 最重要的安全语义）

```
本地上游不可达  →  502 + 明确原因（绝不自动降级到云端）
云端上游不可达  →  502（公开任务失败就是失败，没有隐私风险）
分类引擎异常    →  按 medium，且只走本地上游
```

**网络故障必须朝"更私密"的方向失败，不能朝"更公开"的方向失败。**

这是 v5.1 fallback 逻辑在传输层的对应物，也是测试里必须钉死的一条。
D13 的教训是"修失败点 ≠ 修失败语义"——这条就是 v6 的失败语义。

### 3.7 可观测

响应头（不打断响应体）：

```
x-privacy-gate: level=high rerouted=local tools-stripped=web_search,fetch
x-privacy-gate-session: <session-key 哈希前 8 位>
```

理由见 §7 第 2 条：`reroute` 让判定变得不可见，响应头是唯一的实时出口。

### 3.8 不代理的路径

`/v1/models`、`/healthz` 直接转发/返回；非 `/v1/*` 路径一律 404
（避免被当成通用 HTTP 代理被人白用）。

## 4. 策略层契约（把"开放性"做成一等公民）

### 4.1 先说 v5.1 的一个真实问题

`keywords/rules.json` **看着像契约，其实只有 `keywords` 被引擎读**。
对全仓库 `.py` 检索 `action|description|_schema|_note`：**零匹配**。

后果：使用者要写自己的边界，得先读引擎源码才知道什么有效。
**这跟"开放"是相反的。** 开放的第一步是契约可见。

### 4.2 rules.json schema v4

```json
{
  "schema": "v4",
  "rules": [
    {
      "id": "high-pricing",
      "level": "high",
      "match": { "type": "substring", "pattern": "对外报价" },
      "action": "block_remote",
      "note": "价格口径"
    },
    {
      "id": "high-pricing-regex",
      "level": "high",
      "match": { "type": "regex", "pattern": "(底价|成本价)\\s*(是|多少)" },
      "action": "block_remote"
    },
    {
      "id": "news-exception",
      "level": "none",
      "match": { "type": "substring", "pattern": "收购" },
      "when": { "type": "regex", "pattern": "新闻|公告|公开报道" },
      "action": "allow",
      "note": "公开新闻里的'收购'是误伤，显式豁免"
    }
  ],
  "topic_shift_keywords": ["换个话题", "不谈这个了", "新任务"],
  "remote_tool_patterns": ["*web*", "*fetch*", "*browse*", "*search*"],
  "upstreams": { "cloud": { "...": "..." }, "local": { "...": "..." } }
}
```

要点：

- `match.type` 支持 `substring` / `word`（ASCII 词边界）/ `regex` → **匹配原语可配**，
  不再是引擎里写死的 `_ascii_word_match`
- `action` **真正生效**：`block_remote` / `prefer_local` / `allow`
- `when` 提供豁免条件 → **能表达"这个词别拦"**（v5.1 完全做不到）
- `id` 让决策日志能指向具体规则，统计才做得出来
- 顶层 `topic_shift_keywords` / `remote_tool_patterns` / `upstreams` 也在同一份文件里 → 单一来源

**兼容**：v3 格式自动识别并就地转换（读时转换，写时按新格式落盘），不强迫老用户改文件。

### 4.3 收窄路径（v5.1 缺失的一环）

`correct.py` 目前只能 `append`。而**误伤比漏检更常见**——D13 已经记了
"搜'收购'的公开新闻会被拦成 high"。所以收窄路径比扩充路径更需要工具支持。

```
privacy-gate correct --add    <keyword> --level high
privacy-gate correct --remove <rule-id|keyword>          # 收窄
privacy-gate correct --demote <keyword> --to medium      # 降级
privacy-gate correct --exempt <keyword> --when <regex>   # 豁免
```

每次改动都生成回归用例——**删除和降级也生成**，用来守护"这个词确实不再拦了"。

### 4.4 策略体检（新增）

```
privacy-gate lint            # schema 校验：未知字段、无效 regex、重复 id、层级冲突
privacy-gate stats           # 从决策日志出报告：命中频次、继承率、晋升率、最吵关键词
privacy-gate explain <文本>  # 逐规则跑一遍，说明为什么是这个级别、豁免为何生效或没生效
```

`explain` 是开放性的关键：使用者写了 200 条规则，必须能问"这段话为什么被判 high"。

**为什么 `stats` / `explain` 在 v6 里不是"配套"，而是必需品**：
出厂的粗策略，作者知道它的脾气；一旦边界交给使用者，工具就必须让"这条策略实际会怎么判"
变得可见——否则你开放出去的是一把不知道打哪的枪。

## 5. 适配器矩阵

| 适配器 | 强制强度 | 说明 |
|---|---|---|
| **网关**（`base_url` 指过来） | **强**（在必经路径上） | 主防线；任何 OpenAI 兼容客户端都行 |
| opencode 插件 | 中 | 保留，降级为"标注 + 兜底"，不再承担主防线 |
| Claude Code hook（`PreToolUse`） | 中 | `settings.json` 配置，对 WebFetch/WebSearch 做同样裁决 |
| MCP server | **弱**（自愿调用） | 只做可观测性。**文档必须写明它不能当门禁**，否则是在骗人 |
| 裸 CLI | — | `privacy-gate classify --stdin`，给脚本和管道用 |

## 6. 明确不做的事（吸取 D1 的教训）

- ❌ 难度评分 + 四象限完整实现 → 只做"公开/敏感"二分 + 上游选择
- ❌ 发散通道（小模型脑暴 → 大模型收敛）
- ❌ few-shot 纠正注入
- ❌ 语义模型 / 分词器 → 保持确定性匹配
- ❌ 通用 HTTP 代理（只代理 `/v1/*`）

D1 的教训：**设计文档越长，落地概率越低。** 这份文档的克制本身就是设计的一部分。

## 7. 新增的诚实清单条目

1. **`bash` + `curl` 绕过**：网关在 LLM API 路径上，管不住任意进程出网。
   真要堵得靠系统级出网控制（防火墙只放行网关进程 / 白名单端口）。
   文档给配方，**但本项目不实现**。
2. **`reroute` 让误伤变隐形**：v5.1 里误命中只是"拦一下，你看得见"；v6 里误命中会把请求
   悄悄丢给本地弱模型，用户拿到更差的答案且不知道发生了什么。
   **这等于把门禁的有效性从"召回"转移到"精确"上，而精确恰恰是关键词法最弱的一环。**
   缓解：响应头可见 + `stats` 误伤报告 + 默认记录 reroute 次数。
   这是本设计里最需要被质疑的一处取舍。
3. **工具名依赖**：工具剥夺按名字匹配，命名习惯不同会漏；需要使用者按自己的工具集调模式。
4. **单人 homelab 验证，非生产级**（延续 v5.1）。

## 8. 测试与 CI 计划

- `unittest`（**不引 pytest**，保持零依赖）；现有 42 用例迁移
- 网关管线测试：
  - session key 推导的 5 条优先级，**且兜底是 `default` 而不是新会话**
  - 工具剥夺：命中 / 未命中 / 模式可配
  - **fail-closed 方向性：本地上游不可达时必须 502，绝不能回落到云端**（钉死）
  - SSE 透传：分块到达、不缓冲、错误中途不吞
  - 分类对象只取最后一条 `user` 消息；`role: tool` 不重分类
- 策略层测试：v3 → v4 自动转换、`when` 豁免生效与不生效、`lint` 抓出无效 regex 与重复 id
- `doctor`：**必须能在只读检出下全绿**（延续 D13 第 2 条的教训）
- CI：`ubuntu-latest` + `windows-latest` × Python 3.9 / 3.12 / 3.13
- **零依赖断言**：`pip install .` 之后依赖列表只多自己一个

## 9. 迁移与兼容

- v5.1 插件保留，语义降级：仍在消息上打标注，但不再假设自己是唯一防线
- `rules.json` v3 兼容读，写时升级到 v4（首次写会产生一次大 diff，这是预期的）
- 老用户升级时 `check.py` 会提示 schema 升级

## 10. 实施顺序（每步都能独立验证）

1. **`core/` 解包**：engine / rules / session / log / correct 从 `tools/` 迁到可安装包，
   保持函数签名兼容，回归 42 用例全绿
2. **`rules.json` v4** + 兼容读 + `lint`
3. **`explain` + `stats`**（策略层可观测）
4. **网关**：非流式 → 三种 policy → 工具剥夺 → 流式 → fail-closed 方向性测试
5. **适配器**：Claude Code hook / MCP / CLI
6. **CI** + 零依赖断言 + 英文 README
7. 打 `v6.0.0`

**顺序理由：先把策略层做可见，再做执行层。**
否则网关出问题时，无法判断是策略写错了还是网关有 bug。
