## 导语

我的推理服务器是台 48GB 内存的旧机器，CPU 推理，主力模型是个 35B-A3B 的 MoE，常驻吃掉 22GB。没有 GPU 预算，没有训练条件。

但我需要一个能在本地跑、偶尔联网的 AI Agent——而且它处理的任务里，混着合同、薪酬、客户名单、源码、密钥这些东西。

问题是：**谁来保证这些东西不出内网？**

最开始我把规矩写进 prompt，指望模型自觉。结果多轮对话一长，模型就漂移：说好的"先做隐私检测"会跳步，"禁止联网"会忘。**prompt 是承诺，不是门禁。**

后来我发现，解决这个问题的过程比问题本身有意思——而且最有意思的部分不是"我设计对了什么"，是**我被自己的实现推翻了四次**。

## 第一版：四象限宏大设计

最早我画了一个完整的四象限路由：把每个请求按"隐私程度 × 任务难度"打分，映射到四个象限——低隐私低难度本地小模型直出、低隐私高难度上云端、高隐私低难度本地中等模型、高隐私高难度本地强模型。外加发散通道（小模型脑暴、大模型收敛）和 few-shot 纠错注入。

方案文档写了 700 多行。然后就没有然后了——复杂度超出了单人维护能力。第一课：**设计文档越长，落地概率越低。**

## 第二、三版：上 opencode，用 1.5B 小模型做路由

我把方案落到 opencode 上：一个 1.5B 小模型专职做隐私判定，判定完分发到四个 subagent 流水线（检索→分析→输出→校验），关键词硬规则前置。

跑起来之后，实测给我上了两课：

1. **1.5B 的智力不够做路由。** 对"这段话涉不涉密"的语义判断不可靠，输出格式还经常漂移，准确率不及格。
2. **小模型常驻本身就是成本。** 它抢推理服务器的内存带宽——CPU 推理下带宽是稀缺资源，35B 主模型已经占了 22GB/48GB。

"小模型做路由"是上限，但它有两个隐藏成本：准确率上限，和常驻资源。**资源受限时，先保下限。**

## 第四版：砍到只剩确定性

我把小模型全部砍掉，只留两样东西：

- **代码层关键词规则引擎**：在 LLM 看到输入之前，用确定性匹配检测隐私信号，输出 high / medium / none 三级
- **单一 worker**：一个 35B 模型一站式执行，按级别约束自己的工具使用

级别规则很简单：high 禁所有远程访问，medium 禁抓取网页、搜索仅限公开技术文档，none 全开。**fail-closed**：规则没命中但可能涉密 → 默认按 medium。

这个版本稳定可用。但它有四个洞：

1. 门禁是"模型承诺"不是"代码强制"——worker prompt 里写"必须先跑规则引擎"，但没有机制保证它跑
2. 纠正闭环断了——用户说"这个也算机密"，什么都留不下来，同样的错一直犯
3. 没有决策日志——规则库健康度只能靠感觉
4. 多轮隐私继承丢了——上一轮聊股权（high），下一轮问"那第三条呢"不含关键词 → 判 none → 远程解锁。**这是真实的隐私漏洞。**

## 第五版：补齐四个洞，然后上云

洞 1 用 opencode 插件补：`tool.execute.before` 硬拦截（最可靠的一层）、`permission.ask` 做增强层（这个 hook 历史上有 bug，不能当唯一防线）、worker prompt 手动兜底。消息一进来插件自动跑规则引擎，把 `[系统隐私检测] effective_level=high matched=股权` 注入给模型。

洞 2 用纠正回流补：用户说"这个也算机密"，调一个脚本，关键词进规则表、回归用例自动生成。**没有训练、没有微调、零推理开销。**

洞 3 用决策日志补：每次判定落一条 jsonl，升级频率、最吵的关键词从数据回答。

洞 4 用多轮继承补：按会话建模，不按单条消息建模。

之后又加了一层**云端分层**：公开任务委派云端免费档，敏感任务留本地——"本地脑路由，云手执行公开活"。

## 发布收尾时挖出的两个缺陷（都很典型）

打标签之前我跑了真机验收，挖出两个只在**"不是作者那台机器"**上才暴露的问题：

**① 只读目录下，日志写失败会让整个门禁锁死。** 引擎往 `data/routing_log.jsonl` 追加日志，写不进去就抛异常 → 进程退出码 1 → 插件侧 fail-closed 兜底成 medium → **每条消息都被当作敏感内容，所有远程工具全被拦**。触发条件只是"这个目录不可写"：只读挂载、CI checkout、受限沙箱都算。

**② 体检脚本自己依赖仓库可写。** 它往真实日志写一条记录再清理——于是任何只读检出里它都会报"引擎端到端失败"。这是**假警报**，而且方向恰好相反：它把"你的目录不可写"报告成了"代码坏了"。一个只在作者机器上全绿的体检，比没有体检更糟。

教训一句话：**修失败点 ≠ 修失败语义。** 当时修的是"编码为什么会崩"，没回答"崩了之后该往哪边倒"。所以同一个失败语义换了个触发点又回来了。

## 第六版：把门禁从插件搬到网线上

这是最大的一次结构变化，起因是算账。

第五版的门禁本质上是**一个 hook**。而回顾一下前面所有代价：

- 插件用 TypeScript 写，桌面端的 Node sidecar 加载失败，连 UI 一起失灵（改回 CJS `.js` 才好）
- 桌面端把消息存成 durable event，插件往里新增 part 少个字段就保存失败
- 受限环境下 hook 依赖的那些前提一个个不成立

**这些坑没有一个是我的设计问题，全都来自"依赖别人的 hook"。** 那么换到 Claude Code、Cline、DSH 呢？——只是把同一笔债再欠一次。

所以第六版不换框架，而是**下沉一层**：把强制层放到所有 Agent 的**公共必经之路**上——LLM API 调用本身。

```
Agent ──► 127.0.0.1:8787/v1 ──┬─ none        ──► 云端上游
（任何 OpenAI 兼容客户端）      ├─ medium/high ──► 本地上游（改写 model + 摘掉远程工具）
                              └─ 或 403 拒绝  （block 策略）
```

一个纯标准库的本地网关（没有 FastAPI、没有 Flask，只用 `http.server` 和 `urllib`）。opencode 从此**降级成适配器之一**。

三件机制，按重要性排：

**① 远程工具剥夺。** 敏感会话时，网关把请求体 `tools[]` 里的搜索/抓取工具**摘掉**。模型不是"被要求别调"，是**没有能力调**。这是整个 v6 里唯一一个框架绕不过去的强制点——它不依赖任何 hook、任何插件、任何框架的配合。

**② fail-closed 的方向性。** 本地上游不可达 → 返回 502，**绝不回落到云端**。这一条我认为是整个项目最重要的不变式：本地上游挂了就把请求发给云端，等于**网络故障时自动降级为"数据出网"**。故障必须朝"更私密"的方向倒。它有专门的断言守着——把本地上游指到一个空端口，然后断言云上游收到 **0 个请求**。

**③ 无声重路由。** 敏感会话改写到本地上游并改写 `model`，模型自己都不知道被降级了。

## 适配器矩阵：每个适配器到底有多强

把 opencode 降级成"适配器之一"之后，就得回答一个新问题：**每个适配器有多强？** 含糊其辞会给人虚假的安全感，所以我给每个都标了三件事——强度、是否依赖对方配合、在本机验证到什么程度：

| 适配器 | 强制强度 | 依赖对方配合 | 本机验证 |
|---|---|---|---|
| **网关** | **强** | **否** | 29 条断言 + 真上游实测 |
| opencode 插件 | 中 | 是 | 语法契约 + 每天在用 |
| Claude Code hook | 中 | 是 | 协议逻辑 ✅，**接线未测** |
| MCP server | **弱**（自愿调用） | 是 | 协议层 |

两处刻意的决定：**MCP 适配器只读**——让一个可以被模型调用的接口去改门禁规则，等于把门禁的钥匙挂在门上；**hook 层一律按"会失效"设计**——查上游时发现 Claude Code 的 `PreToolUse` 有一串同类 bug（exit 2 + deny JSON 都没拦住、permissionDecision 被白名单忽略…），跟 opencode 的 `permission.ask` 完全同构。**这不是某个平台的毛病，是"把强制层寄存在别人 hook 上"这类设计的通病。**

## 这次最值钱的收获：五处被我自己推翻的设计

我原本想写"我设计对了什么"。但复盘下来，**被我自己推翻的那五处，比设计本身有用得多**：

**① 豁免的作用域（会造成安全漏洞）。** 规则契约升级后我加了"语境豁免"：某个词在特定语境下不拦。第一版把作用域做成**规则级**。写示例时才发现：给"收购"配一条"公开新闻"豁免，会让**「帮我写保密协议，顺便看看新闻」**因为命中"新闻"把**整条规则**豁免掉——"保密"跟着失效。使用者以为自己受保护，实际上门被自己配的豁免开了。改成**模式级**才正确，现在有一条带 ★ 的回归测试专门守它。

**② `annotate` 策略偷偷改了路由。** 我设计了三档策略，其中 `annotate` 本意是"只观测、不改路由"的演练模式。写测试时发现第一版根本没看 policy，敏感请求被悄悄送到了本地。**它嘴上说不干预，手上在干预。**

**③ 会话键推导：我砍掉了"看起来更聪明"的那一档。** OpenAI API 没有会话概念，而多轮继承要按会话建模。设计文档里我列了五档优先级，其中第四档是"用 system 消息前缀做哈希"。实现时想清楚：它只在客户端每次发同样的 system 消息时才稳定；一旦 system 随请求变化（很多客户端会把工具清单、时间戳塞进去），**每个请求都会得到一个新会话 = none = 解锁远程**。按 fail-closed，不确定时应该落到一个**共享的**兜底键上（宁可过度继承），而不是落到那个"看起来更聪明"的派生键上。

**④ 规则不可用时的 fail-closed：两个分支我只写了一个。** 适配器里我处理了"规则文件解析失败"，但"文件不存在"走的是另一条分支——得到一个**空规则库**，于是新会话被判成 none 并**放行远程工具**。空规则库被当成"正常运行"，正是最不能有的失败方向。推演时觉得"规则不可用"是一个状态，实现时才发现它是两个。

**⑤ 一条 fail-open 路径：我把"看不懂"当成了"公开"。** 这一条不是写代码时发现的，是**写测试时读回那段解析代码**才看见的。

插件里有一个 fail-closed 的 `catch`：调引擎失败就兜底 medium。看起来该做的都做了。但"拿到合法 JSON 却看不懂"落在了另一个分支：

```js
const level = data.effective_level === "high" || data.effective_level === "medium"
  ? data.effective_level
  : "none"          // ← 引擎字段改名 / 引擎返回 {"error":...} → 判为公开
```

于是只要引擎那边改个字段名，门禁就会**把远程工具全打开**。而**所有测试都是绿的**——因为测试只测引擎，插件那半边没人测。

这条的教训比前四条更具体：**fail-closed 是一个关于"所有非成功路径"的性质，不是"catch 块里写个 medium"就完事了。** 梳理失败路径时要连"我没预料到的输入"一起数——那一类最容易漏，因为它**不抛异常**。

**五条的教训是同一条：纸上的设计要靠使用来验证。** 而且不一定是"实现"来推翻——第五条是**写测试**时读回来才看见的。任何试图验证它的动作都会把它翻出来，而推演不会。

所以我现在觉得，"先写一份设计文档给人过目"的价值，**不如"先拿它写一条真规则、跑一次真请求"**。文档可以留，但别指望它把关。

## 还有一条：卖点必须由机器守

项目 README 上写着"零第三方依赖"。写了这句话之后我意识到一件事：**没有任何东西守着它。** 某天有人顺手 `import requests`，这句话就变成谎话——而且是在别人 clone 下来跑不通的时候才发现。

所以我给它配了一条断言：AST 扫全仓库的 import，**动态**判断每个名字装在哪儿（看 origin 里有没有 `site-packages`），而不是查一张会过期的标准库名单。CI 第一步就跑它。

同一条原则还产出了另一个工具：发布前"不暴露内网 IP、主机名、业务关键词"原来也是靠人记得手工跑——而手工检查的问题不是不准，是**下一轮就不会再跑了**。现在它是常驻断言。

这里踩到一个值得记的陷阱：**审计工具不能把敏感词写进自己的代码**，否则它自己就是泄露源——**审计器不该是秘密的副本**。所以扫描器里只有通用类别，项目专属词走一个 gitignore 掉的本地文件。它当场就抓到了我：我在写说明文档时把那几个字面量又抄了一遍，审计器立刻报了出来。

## 最后一条，也是最难自觉的一条：你测的那一层绿了，不代表别的层也对

这个假期我在这上面栽了三次，三次原因各不相同：

**① 三层守卫，只有第一层绿。** 魔搭创空间的引擎与词表是"按字节从主仓库同步"的，
`sync_engine.py --check` 做严格哈希校验。我一直以为"哈希一致 = 页面是对的"。
直到随手跑了一次校验——**它是红的**（漂移很久了没人看）。修完漂移、修完同步清单，
页面**仍然是错的**：渲染层读的是旧版规则结构，那张词表静默变成了空的，而引擎同步得完美无缺。

> 哈希校验能证明"我给过去的东西没变"，证不了"你拿它做的事还对"。

**② 一个文件的两条入口，失败模式毫无重叠。** 把活体项目的引擎指向发布包之后，
插件这条路一切正常——它是 `spawnSync` 起子进程，模块名是 `__main__`。
我据此以为迁完了。然后活体自己的测试脚本崩了：它做的是 `import rules_engine`，
而这时 `sys.modules["rules_engine"]` 里**正是那个转发 shim 自己**，
shim 再 import 同名模块，拿到的是自己的半成品 → 循环导入。
**同一份代码，换个入口就以完全不同的方式失败。**

**③ 检查器自己骗自己。** 我加了一条"文档里写的体检项数必须等于 `check.py` 的项数"。
它当场抓出两处过期的数字，看起来很成功。然后我发现**那条规则本身是错的**：
项数取决于布局（活体多三项、发布包少三项），任何写死的数字必然在两种布局里错一个。
**它抓到的是它自己制造的问题**——一个本不该存在的数字。

三次的共同点：**"绿"都来自一个我看得见的地方，而错发生在一个我没看的地方。**

所以我现在的说法不是"测试过了吗"，而是：

> **我测的是哪一层？还有哪几层没测？**

一个能被机器守住的承诺，也要问它守的是哪一层——传输、消费，还是它自己。

## 核心收获：地板、天花板，和"能被机器守的承诺"

回头看，这套折腾收敛成两个公式：

```
确定性规则保底（地板） + 概率模型求优（天花板） + 人类最终裁决（兜底）
```

- **地板必须是代码**：底线放在模型之外，模型负责执行，规则负责授权
- **授权必须是人**：升级（"这条可以联网"）只能用户发起，模型禁止自我升级
- **闭环不一定要"智能"**：确定性规则 + 人肉标注 + 回归测试守护，是最便宜的学习回路

以及第二个，是这次才想明白的：

```
能被机器守的承诺，不要留在人的记忆里。
```

零依赖、不泄露、策略契约、失败方向——每一条都从"我记得要检查"变成了"它会自己失败给我看"。
